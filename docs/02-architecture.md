# Архитектура Doomatel

Документ описывает устройство системы и, что важнее, **основания** принятых
решений. Решение без основания невозможно ни оспорить, ни пересмотреть
осознанно, поэтому у каждого выбора здесь указано, что именно он покупает
и чем за это платит.

Продуктовый контекст — [01-product.md](./01-product.md).
Модель угроз — [03-security.md](./03-security.md).

---

## 1. Общая схема

```
                    ┌──────────────────────────────────────┐
   браузер ────────►│  apps/web — Next.js                  │
                    │  интерфейс, блочный редактор         │
                    └───────────┬──────────────┬───────────┘
                                │ HTTP         │ WebSocket
                                ▼              ▼
                    ┌────────────────────┐  ┌──────────────────┐
                    │ apps/api — NestJS  │  │ apps/collab      │
                    │ права, данные,     │  │ совместное       │
                    │ журнал действий    │  │ редактирование   │
                    └───┬───────┬────┬───┘  └────────┬─────────┘
                        │       │    │               │
              ┌─────────┘       │    └──────┐        │
              ▼                 ▼           ▼        ▼
    ┌──────────────────┐ ┌───────────┐ ┌─────────────────────┐
    │ PostgreSQL       │ │  Qdrant   │ │ apps/agents — Mastra│
    │ система записи   │ │  поиск    │ │ шесть ролей         │
    │ + политики RLS   │ │           │ │ + рабочие процессы  │
    └────────▲─────────┘ └─────▲─────┘ └──────────┬──────────┘
             │                 │                  │
             │                 │                  ▼
    ┌────────┴─────────────────┴───┐   ┌─────────────────────┐
    │ packages/ingest              │   │ модель по протоколу │
    │ СОЗД, ИС «Законотворчество», │   │ OpenAI-совместимому │
    │ портал правовой информации   │   │ (свой инференс/РФ)  │
    └──────────────────────────────┘   └─────────────────────┘
```

**Почему сервисы разделены.** Работа агента над законопроектом занимает
минуты и удерживает большой контекст. В одном процессе с обработкой обычных
запросов это означало бы, что тяжёлый запуск влияет на отзывчивость
интерфейса. Разделение позволяет масштабировать их независимо: интерфейсу
нужно много лёгких обработчиков, агентам — мало тяжёлых.

## 2. Состав репозитория

| Путь | Назначение |
|---|---|
| `packages/legal` | предметная область: разбор ссылок, структура актов, экспертиза |
| `packages/ingest` | источники данных: транспорты, клиенты, парсеры |
| `packages/db` | схема, миграции, политики доступа |
| `packages/retrieval` | лексика, разбиение на фрагменты, гибридный поиск |
| `apps/api` | прикладной сервис: права, данные, журнал |
| `apps/agents` | агенты и рабочие процессы |
| `apps/web` | интерфейс |
| `infra` | локальная инфраструктура |

Зависимости направлены в одну сторону: `apps/*` → `packages/*`, и никогда
обратно. Предметная область (`packages/legal`) не знает ни о базе, ни о сети —
поэтому её можно проверить тестами без окружения, что и сделано.

## 3. Данные

### 3.1. Единственная система записи

**Решение: PostgreSQL — единственный источник истины. Всё остальное —
производные представления, восстановимые из него.**

Что это означает на практике:

- векторный индекс в Qdrant можно удалить и пересобрать из базы,
  не обращаясь к источникам заново;
- граф связей между нормами — таблица `legal_edge` и рекурсивные запросы,
  а не отдельная база;
- состояние приостановленных рабочих процессов хранится в базе, поэтому
  документ, ожидающий визы, переживает перезапуск сервиса.

**Отвергнутая альтернатива: TypeDB.** Выразительность языка запросов реальна,
но драйвер для Node.js не переведён на третью версию: единственный путь
из TypeScript — обёртка поверх HTTP без пула соединений и потоковой передачи.
Цена — потеря разграничения доступа на уровне строк, транзакционной
целостности с остальными данными и возможности мигрировать. Если обходы
графа однажды упрутся в производительность, специализированный движок
подключается как **производное** представление, не как система записи.

### 3.2. Схемы

Две схемы с разными правилами доступа:

- **`legal`** — корпус законодательства. Данные официальные: официальные
  документы государственных органов не являются объектами авторских прав
  (подпункт 1 пункта 6 статьи 1259 Гражданского кодекса). Чтение открыто
  всем аутентифицированным пользователям, запись — только сервису ингеста.
- **`public`** — прикладные данные: организации, проекты, документы, чаты,
  задачи. Строгие политики доступа.

### 3.3. Время в модели права

Редакции актов моделируются по двум независимым осям времени:

- `validFrom` / `validTo` — период действия нормы;
- `knownFrom` / `knownTo` — период, когда система знала об этой версии.

Первая ось отвечает на вопрос «что действовало на дату D». Вторая —
на вопрос «что мы считали действующим на дату D», без которого невозможно
объяснить, почему полгода назад помощник ответил иначе.

Уровни модели соответствуют FRBR: `legal_work` (акт), `legal_expression`
(редакция), `legal_unit` (структурная единица).

### 3.4. Устойчивые идентификаторы

```
eli:rf:federal-law:2006-07-27:149-fz                    — акт
eli:rf:federal-law:2006-07-27:149-fz@2024-08-08         — редакция
eli:rf:federal-law:2006-07-27:149-fz@2024-08-08#st_15/p_3 — норма
```

Идентификатор не зависит от внутренних ключей источника, читается человеком
и служит якорем цитаты в ответе помощника. Схема следует подходу European
Legislation Identifier, адаптированному под российские реквизиты;
российского обязательного стандарта машиночитаемых актов не существует.

## 4. Разграничение доступа

### 4.1. Задача

Депутаты разных партий работают в одной системе. Материалы законопроекта
до внесения — сведения, утечка которых имеет политические последствия.
При этом межфракционная работа должна быть возможна.

### 4.2. Решение

Доступ к проекту возникает по одному из пяти оснований, и итоговая роль —
наибольшая из них:

1. владелец проекта;
2. прямое участие (в том числе приглашённый из другой партии);
3. членство в организации-владельце;
4. членство в рабочей группе-владельце;
5. доступ, выданный организации или рабочей группе целиком, с сроком.

Всё это вычисляет одна функция `public.project_role`. Ключевое свойство:
она объявлена `SECURITY DEFINER`, иначе политика на таблице проектов
обращалась бы к таблице участников, политика на участниках — обратно
к проектам, и запрос уходил бы в бесконечную рекурсию.

### 4.3. Единственный источник видимости

`public.visible_project_ids` и `public.visible_tenant_ids` — единственное
место, где вычисляется, что пользователь видит. **Этими же перечнями
ограничивается выдача векторного поиска.**

Это не украшение архитектуры. Если бы политики базы и фильтр поиска считали
видимость независимо, их расхождение означало бы утечку материалов между
фракциями — и ничто бы её не обнаружило, потому что каждая часть по
отдельности вела бы себя правильно.

### 4.4. Граница «спрашиваю о себе»

Функции доступа находятся в схеме `public` и потому доступны как методы RPC.
Без ограничения любой депутат мог бы перебором выяснить, кто в каком чужом
проекте участвует. Функция `assert_self` это запрещает.

Признак обращения от имени сервиса определяется **по отсутствию
удостоверения**, а не по роли: внутри функции `SECURITY DEFINER` текущая
роль равна владельцу функции, поэтому проверка роли всегда давала бы
«сервис». Это выяснилось на практике — первая версия проверки не срабатывала
именно по этой причине.

### 4.5. Почему `LANGUAGE sql`, а не `plpgsql`

Распространённое требование — писать вспомогательные функции только
на plpgsql, иначе планировщик встроит их и «граница прав исчезнет».
Проверено экспериментом на PostgreSQL 16:

| Функция | План запроса |
|---|---|
| `LANGUAGE sql STABLE` | встроена: условие свёрнуто в Index Scan |
| то же + `SECURITY DEFINER` | **не встроена**: вызов остался как Filter |
| то же + `SET search_path` | **не встроена** |

Вывод: `SECURITY DEFINER` сам по себе запрещает встраивание. Переписывать
функции на plpgsql ради этого не нужно — это была бы реальная работа
и реальный риск регрессии без выигрыша.

## 5. Поиск

### 5.1. Почему гибридный, а не векторный

Чисто смысловой поиск систематически промахивается по точным реквизитам:
«149-ФЗ», «статья 15.1», «часть 3». Для законотворчества это неприемлемо —
депутат ищет конкретную норму, а не похожую по смыслу.

Три независимые ветви объединяются ранговым слиянием:

1. **плотная** — смысловая близость;
2. **разрежённая** — совпадение слов после приведения к основам;
3. **точная по реквизитам** — совпадение номера акта.

Слияние по рангам, а не по значениям близости: оценки лексического
совпадения и косинуса несопоставимы по масштабу, и масштаб первого
смещается по мере роста корпуса, который пополняется ежедневно.

### 5.2. Разбиение по структуре, а не по длине

Границы фрагментов совпадают с границами статей. Причина: ответ обязан
содержать точную ссылку, а ссылка на «фрагмент с 4200-го символа»
бессмысленна. Фрагмент, разрезающий статью посередине, теряет условие
или исключение — и норма читается неверно.

Короткие статьи объединяются, длинные делятся по абзацам с перекрытием.

### 5.3. Ограничение выдачи

Права применяются **на сервере** и добавляются к любому фильтру, каким бы
он ни пришёл. Модель не может расширить себе доступ, даже если содержимое
документа попытается её к этому склонить.

## 6. Агенты

### 6.1. Почему шесть ролей, а не один помощник

У задач разная цена ошибки. Аналитику допустимо ошибиться в подборе
практики — это исправит человек. Составителю нельзя ошибиться в реквизитах
изменяемой нормы: такая ошибка в поправке ко второму чтению делает поправку
неисполнимой. Поэтому у составителя жёстче инструкции, ниже температура
и прямой запрет воспроизводить нормы по памяти.

Координатор намеренно лишён предметных инструментов: имея их, он начинает
отвечать сам, теряя специализированные инструкции профильных агентов.

### 6.2. Что делает программа, а что — модель

Разделение проведено по одному признаку: **есть ли у задачи проверяемый
правильный ответ**.

| Программа | Модель |
|---|---|
| разбор ссылок на нормы | оценка существенности замечания |
| разбор структуры акта | формулировка вывода |
| поиск языковых маркеров | оценка, присутствует ли фактор |
| построение цитаты | выбор релевантной нормы |

Там, где правильный ответ существует, программа надёжнее. Маркер вроде
слова «вправе» — это **место для оценки**, а не нарушение: выдавать его
за нарушение означало бы завалить эксперта ложными срабатываниями.

### 6.3. Человек в контуре

Рабочий процесс подготовки законопроекта приостанавливается перед выпуском
и ждёт визы. Приостановка сохраняется в базе, поэтому ожидание не занимает
ресурсов и переживает перезапуск.

Агент не изменяет документы напрямую — он создаёт предложения правок,
которые человек принимает или отклоняет.

### 6.4. Модели

Единственный поддерживаемый способ подключения — эндпоинт, совместимый
с протоколом OpenAI. Под него подходят и собственный инференс, и российские
сервисы. Агенты получают **роль** модели («основная», «быстрая», «длинный
контекст»); сопоставление роли конкретной модели — вопрос конфигурации.

При отсутствии настройки сервис **не запускается**. Молчаливый переход
на внешний сервис в этом контуре недопустим.

## 7. Источники данных

### 7.1. Транспорт как интерфейс

Источники доступны по-разному: часть закрыта извне России, часть требует
клиентского рендеринга, часть отдаёт содержимое в однобайтовой кодировке.
Транспорт вынесен в интерфейс: прямой HTTP, HTTP через прокси, браузер
и воспроизведение записанных снимков взаимозаменяемы.

### 7.2. Разработка против снимков

Парсеры разрабатываются против записанных снимков страниц и покрыты
тестами; снимки снимаются командой изнутри контура. Это единственный способ
получить воспроизводимую проверку парсера источника, недоступного
из среды разработки.

### 7.3. Ловушки источников — закреплены тестами

Две ошибки стоят дороже остальных, поэтому вынесены в отдельные функции
и покрыты тестами, объясняющими причину:

- **Пагинация СОЗД.** В расширенной форме параметр страницы называется
  `page_{GUID}`; обычный `page` молча игнорируется, и обход бесконечно
  собирает первую страницу, выглядя успешным.
- **Наименования фаз не уникальны.** Три чтения имеют одинаковое название
  фазы и различаются только стадией. Сопоставление событий по названию
  молча смешает три чтения в одно.

## 8. Что осталось нерешённым

Перечислено явно, чтобы не выглядело решённым:

1. **Источник действующих редакций** — см. [01-product.md](./01-product.md), Р1.
   Определяет полезность продукта целиком.
2. **Поддержка вызова инструментов российскими моделями** — не проверена.
   Без неё конструкция агентов не работает.
3. **Отслеживание изменений в редакторе** — открытые решения ограничены;
   выбор между собственной реализацией поверх предложений правок
   и платным расширением не сделан.
4. **Разбор изображений актов** — портал правовой информации публикует
   акты изображениями; ветка распознавания обязательна и не реализована.
5. **Память агентов вне модели доступа** — история диалогов содержит
   содержимое документов, но хранится вне политик разграничения.
   Требует решения до опытной эксплуатации.
